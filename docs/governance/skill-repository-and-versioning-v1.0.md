# 通用 Skill 仓库与版本管理规范 V1.0

- **文档编号：** NCS-GOV-001
- **文档版本：** 1.0.0
- **状态：** 首版治理规范
- **适用范围：** 本仓库内的总控 Skill、创作工作流 Skill、专项能力 Skill、小说类型扩展包及其项目引用
- **上位文件：** 《通用小说创作 Skill 体系架构 V0.1》
- **权威仓库：** https://github.com/wenzhong0606-dev/novel-creation-skills

---

## 1. 目的与基本原则

本规范建立通用小说创作 Skill 资产的统一组织、描述、验证、版本发布、项目引用和生命周期治理机制。

目标不是增加文档或流程负担，而是确保：

1. 每项能力有稳定身份、明确职责和可识别的入口文件。
2. 使用者能够判断该能力适用于什么任务、需要什么输入、会交付什么结果。
3. 不同 Skill 可以组合调用，同时避免职责重叠、依赖不明和版本冲突。
4. 能力成熟度由真实任务证据支持，而不是由作者自评或版本号推定。
5. 小说项目能够固定使用某个确切版本，不因通用仓库更新而意外改变。
6. 历史版本、变更原因、验证结果和回滚路径可追溯。
7. 通用方法、类型扩展和单部小说项目资料保持边界清晰。

### 1.1 规范用语

- **必须**：不满足即视为不符合本规范。
- **应该**：通常应当遵守；如有合理例外，必须记录原因。
- **可以**：允许采用，但不构成强制要求。

### 1.2 治理原则

- **职责单一**：一个 Skill 应有清楚的主要任务，不把多个独立能力无边界地塞进同一模块。
- **契约优先**：输入、输出、前置条件和边界比提示词长度更重要。
- **证据优先**：成熟度升级必须有实际使用和评测证据。
- **版本可复现**：项目正式使用的 Skill 必须能定位到不可歧义的仓库版本。
- **向后兼容意识**：修改前先判断对现有项目和依赖 Skill 的影响。
- **历史可追溯**：不通过覆盖历史、重写已发布标签或删除旧版本来掩盖变化。
- **适度治理**：尚无实际 Skill 时不预建大量空目录；治理成本应与能力数量和风险相称。

## 2. 资产类型与版本边界

本仓库管理三类资产：

| 资产类型 | 定义 | 主要位置 | 独立版本 |
|---|---|---|---|
| 总控 Skill | 识别任务、组织工作流、调度能力 | skills/orchestrator/ | 是 |
| 创作工作流 Skill | 完成相对完整的创作任务 | skills/workflows/ | 是 |
| 专项能力 Skill | 执行可被多个工作流复用的专项任务 | skills/specialized/ | 是 |
| 小说类型扩展包 | 为多个工作流和专项能力提供类型约束、方法和评测 | extensions/genres/ | 是 |

前三类属于三层功能架构；小说类型扩展包是横向扩展资产，不构成第四层。

单部小说的世界观、人物档案、故事规划、正文、项目决策、评审记录和进度资料不属于通用 Skill 资产，必须留在对应小说项目的权威存储位置。

### 2.1 三种版本号不得混用

必须区分：

1. **单项 Skill / 扩展包版本**：描述某一项能力本身的版本，采用语义化版本号。
2. **仓库目录快照版本**：描述某个时间点仓库中一组资产的组合状态；仅在需要发布可复现的整套目录快照时使用。
3. **治理文档版本**：描述本规范自身的修订版本。

某项 Skill 升级，不代表所有 Skill 都升级；治理文档升级，也不自动改变任何 Skill 的版本。

## 3. 仓库目录与文件组织

### 3.1 目录约定

仓库采用以下逻辑结构。目录在有真实内容时创建，不为尚未开发的能力建立空目录。

~~~text
novel-creation-skills/
├── README.md
├── VERSION
├── CHANGELOG.md
├── SKILL_INDEX.md
├── docs/
│   ├── architecture/
│   ├── governance/
│   └── integration/
├── skills/
│   ├── orchestrator/
│   │   └── <skill-id>/
│   ├── workflows/
│   │   └── <skill-id>/
│   └── specialized/
│       └── <skill-id>/
├── extensions/
│   └── genres/
│       └── <extension-id>/
├── templates/
└── evaluations/
~~~

### 3.2 单项 Skill 标准目录

每个正式 Skill 使用独立目录，目录名必须与稳定 Skill ID 一致。

~~~text
<skill-id>/
├── SKILL.md
├── manifest.yaml
├── CHANGELOG.md
├── references/       # 可选：必要的参考规范或方法资料
├── templates/        # 可选：执行时使用的模板
├── examples/         # 可选：经过说明的示例
└── evaluations/      # 应有：验证案例、结果或评测索引
~~~

文件职责：

| 文件/目录 | 要求 | 职责 |
|---|---|---|
| SKILL.md | 必须 | 人和执行模型阅读的主说明，包含完整职责、触发、输入、流程、输出和边界 |
| manifest.yaml | 必须 | 机器和总控层可读取的结构化元数据 |
| CHANGELOG.md | 必须 | 记录该 Skill 各版本变化 |
| evaluations/ | 应有 | 保存或索引测试案例、评审记录和验证证据 |
| references/ | 可选 | 仅放执行确实需要的补充资料 |
| templates/ | 可选 | 可复用交付模板 |
| examples/ | 可选 | 解释正确用法、边界和典型失败的示例 |

不得把所有内容都堆入 SKILL.md。主文件应能独立说明如何调用该能力；过长的参考材料可拆分到 references，并在主文件中明确指出何时读取。

### 3.3 类型扩展包标准目录

~~~text
<extension-id>/
├── EXTENSION.md
├── manifest.yaml
├── CHANGELOG.md
├── references/       # 可选
├── templates/        # 可选
└── evaluations/      # 应有
~~~

EXTENSION.md 必须说明类型读者承诺、适用范围、类型规则、与通用方法的关系、可能影响的工作流和专项能力，以及不能覆盖的项目约束。

### 3.4 文件格式

- 主要说明文件使用 UTF-8 编码的 Markdown。
- 结构化元数据使用 YAML。
- 评测数据优先使用易读、可版本比较的 Markdown、YAML 或 JSON。
- 文件名使用小写英文 kebab-case；正式中文文档标题可使用中文。
- 不将只有截图、聊天链接或无法检索的图片作为唯一规范内容。
- 外部资料必须记录来源和使用目的；引用内容应遵守相应版权要求。

## 4. 命名与稳定身份

### 4.1 Skill ID

Skill ID 必须满足：

- 使用小写英文和连字符。
- 以职责为中心，避免使用临时项目名、日期或版本号。
- 一经正式登记，不因显示名称微调而改变。
- 不把版本号写进 ID。
- 不将不同职责的能力共用一个 ID。

推荐形式：

| 层级 | ID 示例 | 目录示例 |
|---|---|---|
| 总控层 | orchestrator-novel-project | skills/orchestrator/orchestrator-novel-project/ |
| 工作流层 | workflow-character-system-design | skills/workflows/workflow-character-system-design/ |
| 工作流层 | workflow-emotional-architecture | skills/workflows/workflow-emotional-architecture/ |
| 专项能力层 | specialized-causal-chain-audit | skills/specialized/specialized-causal-chain-audit/ |
| 类型扩展 | genre-mystery | extensions/genres/genre-mystery/ |

以上仅为命名示例，不表示这些 Skill 已经创建或达到任何成熟度。

### 4.2 名称与 ID 的区别

- ID 是稳定标识，用于目录、依赖、索引和项目锁定。
- name 是面向使用者的名称，可以调整措辞。
- description 是简明用途说明，不得替代完整职责边界。

### 4.3 重命名、拆分与合并

- 只改显示名称、不改职责和身份时，保留 ID。
- 主要职责发生变化、原 ID 已不再准确时，应创建新 ID，并将旧 Skill 标记为 Deprecated。
- 一个 Skill 拆成多个 Skill 时，新 Skill 使用新 ID；旧 Skill 保留迁移说明。
- 多个 Skill 合并时，指定一个新主 ID 或明确保留的 ID，并为其他 ID 提供迁移说明。
- 不得把旧 ID 静默改作完全不同的能力。

## 5. Skill 契约与元数据规范

### 5.1 SKILL.md 必须包含的章节

每个正式 Skill 的 SKILL.md 至少包含：

1. **身份与定位**：名称、ID、所属层级、职责摘要。
2. **目标与非目标**：解决什么问题，明确不负责什么。
3. **触发条件**：何时调用，何时不应调用。
4. **输入要求**：必需材料、可选材料、来源优先级和缺失处理。
5. **前置条件**：开始前必须确认的事实、决策和项目约束。
6. **执行流程**：可执行的步骤、判断点、分支和复核方法。
7. **输出契约**：交付物、格式、必含字段和证据要求。
8. **质量标准**：如何判断完成、失败或需要返工。
9. **边界与升级处理**：遇到冲突、证据不足或超出权限时如何处理。
10. **依赖关系**：调用其他 Skill 的条件和所需版本。
11. **验证说明**：已验证的项目、任务类型、案例位置和已知局限。
12. **版本信息**：当前版本、成熟度、变更记录入口。

若某章节确实不适用，必须明确写“不适用”及理由，不得直接省略关键边界。

### 5.2 manifest.yaml 必需字段

每个 Skill 的 manifest.yaml 至少包含：

~~~yaml
id: workflow-character-system-design
name: 人物体系设计
version: 0.1.0
maturity: draft
lifecycle: active
layer: workflow
description: 设计人物动机、关系、行为约束与人物弧光。
entrypoint: SKILL.md
scope:
  includes:
    - 人物目标与动机
    - 人物关系与冲突
    - 人物弧光和关键选择
  excludes:
    - 代写小说正文
inputs:
  required:
    - 项目总纲或当前故事规划
  optional:
    - 已有角色档案
outputs:
  - 人物档案
  - 人物关系网络
  - 人物弧光与关键选择表
dependencies: []
compatibility:
  orchestrator: ">=0.1.0"
evidence:
  projects: []
  evaluations: []
last_reviewed: 2026-11-26
~~~

以上是字段示例，不是已创建 Skill 的真实登记。实际值必须与 SKILL.md 一致。

字段规则：

| 字段 | 必须性 | 规则 |
|---|---|---|
| id | 必须 | 全仓库唯一、稳定、符合命名规范 |
| name | 必须 | 中文或英文显示名称 |
| version | 必须 | 单项资产的语义化版本 |
| maturity | 必须 | Draft、Experimental、Project-validated、Cross-project-validated、Stable 之一 |
| lifecycle | 必须 | Active、Deprecated、Archived 之一 |
| layer | Skill 必须 | orchestrator、workflow、specialized 之一；类型扩展使用 extension |
| description | 必须 | 一至数句说明用途和主要边界 |
| entrypoint | 必须 | 主入口文件相对路径 |
| scope | 必须 | 包含与排除的职责 |
| inputs | 必须 | 必需和可选输入 |
| outputs | 必须 | 可验收的输出 |
| dependencies | 必须 | 无依赖时写空数组 |
| compatibility | 必须 | 兼容的总控层或依赖版本范围；不适用时明确说明 |
| evidence | 必须 | 项目和评测证据索引；尚无证据时使用空数组 |
| last_reviewed | 必须 | 最近一次完整复核日期 |

类型扩展包采用相同的身份、版本、成熟度、生命周期和证据原则，但其 layer 为 extension，入口为 EXTENSION.md，并额外说明适用类型和影响范围。

### 5.3 元数据一致性

manifest.yaml 是结构化登记的权威文件；SKILL.md 是详细执行说明的权威文件。二者不得互相矛盾。

每次发布必须检查：

- ID、版本、成熟度和生命周期一致。
- 输入输出与主说明一致。
- 依赖版本与兼容声明一致。
- 证据链接真实存在且能支持所声明的成熟度。
- 入口文件和引用路径有效。

## 6. 成熟度与生命周期

成熟度描述能力经过多少验证；生命周期描述该资产是否仍在维护。两者必须分开管理。

### 6.1 成熟度等级

| 成熟度 | 定义 | 升级所需证据 |
|---|---|---|
| Draft | 已有设计和职责边界，尚未完成真实任务验证 | 设计、契约和待验证清单 |
| Experimental | 已在真实任务中试用，方法、流程或边界仍可能明显变化 | 至少一次真实使用记录，明确记录问题和局限 |
| Project-validated | 已在一个明确小说项目中完成重复使用和复核，证明在该项目范围内可执行 | 至少两个不同任务实例或一个完整工作流周期；有产出、问题和复核记录 |
| Cross-project-validated | 已在至少两个独立小说项目中验证，且结果支持复用 | 两个项目的实际使用证据、差异分析、适用范围与失败边界 |
| Stable | 契约、流程、质量标准和失败处理已稳定，具备可重复使用证据 | 完整文档、有效评测、已知局限、依赖兼容和维护责任；若宣称通用跨项目适用，必须先达到 Cross-project-validated |

补充规则：

1. 成熟度不由版本号自动决定。
2. 不能仅凭一次成功输出、作者自评或无硬伤评审升级。
3. 不同类型的 Skill 可以有不同评测标准，但必须有可复核证据。
4. Cross-project-validated 表示在不同小说项目中验证，不自动等于跨所有小说类型验证。
5. Stable 必须写明适用范围；不得用 Stable 暗示它适用于未经验证的所有类型。
6. 若新证据暴露重大缺陷，可以将成熟度降回 Experimental 或 Project-validated，并记录原因。

### 6.2 生命周期状态

| 状态 | 含义 | 使用规则 |
|---|---|---|
| Active | 正常维护和使用 | 可以被新项目采用，前提是成熟度符合项目风险要求 |
| Deprecated | 已宣布不建议新项目采用 | 现有项目可在迁移期内继续锁定旧版本；必须说明替代方案 |
| Archived | 停止维护，仅为历史和复现保留 | 不得作为新项目默认依赖 |

Deprecated 和 Archived 不是成熟度等级。被弃用的 Skill 仍保留其最后一次成熟度记录。

### 6.3 使用门槛

- Draft：只用于设计讨论，不得作为正式执行依据。
- Experimental：仅在明确标注实验性质、允许复核和回滚的任务中使用。
- Project-validated：可以在已验证范围内用于正式项目。
- Cross-project-validated：可以在已验证的项目范围内作为跨项目复用候选。
- Stable：可以作为默认复用候选，但仍须核对类型、项目约束和版本兼容性。

## 7. 语义化版本规范

每项 Skill 和类型扩展包独立采用 MAJOR.MINOR.PATCH 版本号，例如 1.2.3。

### 7.1 版本递增规则

| 版本位 | 适用变化 | 示例 |
|---|---|---|
| MAJOR | 不兼容变化 | 改变职责边界、必需输入、输出结构、核心流程或依赖契约，导致既有项目需要调整 |
| MINOR | 向后兼容的能力增加 | 新增可选输入、可选检查、可选输出或兼容的新分支 |
| PATCH | 不改变外部行为的修正 | 错别字、路径修复、说明澄清、内部整理且不改变执行结果 |

判断标准：

- 如果原有项目不修改配置和调用方式就无法继续正确使用，通常是 MAJOR。
- 如果原有调用仍然有效，只是获得新能力，通常是 MINOR。
- 如果外部可观察行为和契约不变，只修正文档或内部表达，通常是 PATCH。
- 仅仅把提示词改得更长或更短，不构成版本升级理由；必须说明实际变化。

### 7.2 预发布版本

尚未达到 Stable 的能力可以使用 0.x.y；需要发布候选版本时可以使用 alpha、beta 或 rc 标识，例如 0.4.0-beta.1。

- 0.x 阶段不承诺完整的向后兼容，但每次变化仍必须记录。
- 进入 Stable 时，应具备完整契约并发布 1.0.0。
- 1.0.0 之后严格按 MAJOR.MINOR.PATCH 规则递增。
- 成熟度与版本号相互独立，不能把“版本高”当成成熟证据。

### 7.3 已发布版本不可改写

- 每个正式版本必须对应一个 Git commit 和不可歧义的 Git tag。
- 已发布 tag 不得移动、覆盖或重新指向其他 commit。
- 发现发布错误时，发布新的修正版本；必要时将错误版本标记为 Deprecated。
- 不使用 force push 改写已发布历史。

### 7.4 标签命名

建议采用：

- 单项 Skill：skill-<skill-id>-vX.Y.Z
- 类型扩展包：extension-<extension-id>-vX.Y.Z
- 整体仓库快照：catalog-vX.Y.Z

单项 Skill tag 代表该 Skill 在对应 commit 上的确切内容；catalog tag 代表整套目录在该 commit 上的快照。没有必要时，不发布 catalog tag。

## 8. 变更、评测与发布流程

任何正式版本发布均应经过以下流程。

### 8.1 变更提案

先记录：

- 为什么需要改变。
- 当前方法的具体问题或新需求。
- 哪些项目、工作流和依赖 Skill 可能受影响。
- 预期改善及可能风险。
- 是否涉及已确认的项目决策。

不得只以“优化一下”“感觉更好”作为完整变更依据。

### 8.2 影响分析

检查：

- 是否改变 Skill 的职责边界。
- 是否改变必需输入、输出或执行顺序。
- 是否影响总控层调度。
- 是否影响依赖该 Skill 的其他 Skill。
- 是否影响已锁定该版本的小说项目。
- 是否需要迁移指南或替代方案。

### 8.3 实施与评测

- 修改 SKILL.md、manifest.yaml 和必要的参考文件。
- 添加或更新评测案例。
- 对关键判断设置正例、反例和边界案例。
- 检查输出是否符合契约。
- 记录失败、误判、例外和需要人工判断的情况。
- 不得只展示成功案例而隐藏失败案例。

### 8.4 复核与批准

发布前至少检查：

1. 文件结构与命名合规。
2. 元数据与说明一致。
3. 依赖和兼容声明有效。
4. 评测证据支持拟声明的成熟度。
5. 变更级别与版本号相符。
6. CHANGELOG 已更新。
7. SKILL_INDEX 已更新。
8. 不会静默改变已锁定项目的使用版本。

作者和复核者可以是同一人，但高风险、重大版本和成熟度升级应该尽量进行独立复核。正式发布由仓库维护责任人批准。

### 8.5 发布

发布时必须：

- 更新 manifest.yaml 中的版本和成熟度。
- 更新该 Skill 的 CHANGELOG.md。
- 更新根目录 SKILL_INDEX.md。
- 确认所有依赖和测试证据。
- 创建对应版本 tag。
- 在需要时更新仓库整体 CHANGELOG.md。
- 保留发布 commit、tag 和验证记录。

### 8.6 发布后观察

发布后若发现实际使用与预期不符，应建立问题记录，评估是否需要 PATCH、MINOR、MAJOR 或直接 Deprecated。不得为了维护版本号好看而延迟记录重大问题。

## 9. 项目引用、版本锁定与升级

### 9.1 项目级清单

每部小说项目必须维护 PROJECT_SKILLS.md，记录该项目实际采用的通用 Skill 和类型扩展包。

至少包含：

| 字段 | 说明 |
|---|---|
| ID / 名称 | 被引用资产的稳定标识 |
| 版本 | 单项 Skill 或扩展包版本 |
| 成熟度 | 引用时已声明的成熟度 |
| 来源路径 | 仓库内的准确路径 |
| 来源仓库 | 权威 GitHub 仓库 |
| Git tag | 对应发布标签；如无正式标签，应明确说明 |
| Commit SHA | 精确定位实际内容的 commit |
| 项目配置 | 本项目启用、禁用或适配的参数 |
| 状态 | Enabled、Disabled 或 Trial |

正式创作基线应锁定精确 commit SHA。版本号和 tag 便于阅读，commit SHA 用于精确复现。

### 9.2 不允许隐式跟随主分支

- 正式项目不得仅写 main、latest 或“最新版”作为版本锁定。
- 使用 main 进行试验时，必须标注 Trial，并记录当次 commit SHA。
- 仓库更新不自动更新项目锁定版本。
- 项目升级必须经过影响分析、样例验证和项目负责人确认。
- 已锁定的项目可以继续使用旧版本，不因新版本发布而被迫升级。

### 9.3 依赖锁定

- Skill 声明的依赖必须有版本范围和职责说明。
- 项目采用某 Skill 时，必须同时确认其依赖兼容。
- 关键依赖应在项目级清单中明确锁定。
- 不得因依赖 Skill 发布新版本就自动升级调用方。
- 依赖升级后，必须复核调用方的输出契约和评测结果。

### 9.4 项目适配与覆盖

项目特定要求优先放在小说项目自己的配置或说明文件中，不直接修改通用 Skill 来满足单一项目需求。

适配必须说明：

- 适配原因。
- 适用项目。
- 覆盖或补充了哪项默认规则。
- 是否改变 Skill 原有输出或行为。
- 是否有必要将该适配提炼成通用改进或类型扩展。

若适配改变通用 Skill 的核心行为，应通过正式变更流程发布新版本，不能只在项目里悄悄改写其副本。

### 9.5 升级流程

1. 比较当前锁定版本与候选版本的变更。
2. 检查 MAJOR/MINOR/PATCH 级别和兼容说明。
3. 识别对本项目设定、工作流、历史产出和依赖的影响。
4. 选择有代表性的既有任务进行回归验证。
5. 记录差异、收益、风险和未解决问题。
6. 由项目负责人批准后更新 PROJECT_SKILLS.md。
7. 保留升级前的版本和 commit，确保可以回滚。

## 10. 弃用、归档与回滚

### 10.1 Deprecated

决定弃用时，必须在 manifest.yaml 和 CHANGELOG.md 中记录：

- 弃用原因。
- 生效版本或日期。
- 是否存在替代 Skill。
- 替代 Skill 的 ID 和建议版本。
- 迁移步骤及可能损失。
- 现有项目是否可以继续使用旧版本。

若存在重大错误或风险，可以立即停止新项目采用，不必等待常规迁移期。

### 10.2 Archived

满足以下条件时可以归档：

- 已无新项目采用。
- 迁移说明和替代关系已经明确，或明确不存在替代方案。
- 历史项目仍可能需要复现，因此保留全部内容和版本记录。

归档不等于删除。历史引用必须仍能定位到对应文件和 commit。

### 10.3 回滚

回滚应通过项目锁定版本恢复或发布新的修正版本实现：

- 项目级回滚：将 PROJECT_SKILLS.md 恢复到此前已验证的版本和 commit。
- 仓库级修正：发布新的 PATCH 或其他适当版本。
- 不删除问题版本，不移动历史 tag，不用强制推送掩盖错误。
- 记录回滚原因、影响项目、恢复版本和后续修复计划。

## 11. 仓库治理责任

治理职责按角色定义，不预设由某个具体人员永久承担。

| 角色 | 主要责任 |
|---|---|
| 仓库所有者 | 确认总体方向、治理规则和重大变更 |
| 维护责任人 | 管理目录、索引、版本、发布和弃用记录 |
| Skill 作者 | 维护方法、契约、评测案例和变更说明 |
| 复核者 | 检查正确性、兼容性、证据和风险 |
| 小说项目负责人 | 决定项目采用、升级、覆盖或停用哪些 Skill |

同一人可以承担多个角色，但职责和决策记录必须清楚。

AI 可以承担资料整理、方法分析、草案撰写、测试执行、差异分析和变更建议；不得把尚未验证的推断写成已验证事实，也不得未经授权改变项目已批准的 Skill 锁定和创作基线。

### 11.1 冲突优先级

当通用 Skill 建议与项目约束冲突时：

1. 先指出具体冲突及证据。
2. 区分是项目特殊要求、通用方法缺陷，还是输入资料不完整。
3. 说明对质量和后续任务的影响。
4. 提出保留项目约束、调整调用方式或升级 Skill 的备选处理。
5. 由项目负责人决定是否变更项目基线。

不得静默覆盖已确认的项目决策。

## 13. 当前仓库的落地规则

本规范发布时，仓库仍处于架构与治理基础建设阶段，尚未正式登记具体 Skill。因此：

1. 本规范先建立标准，不立即创建全部候选 Skill 的空目录。
2. 现有架构文档继续保留其独立版本，不因本规范发布而改名或改写。
3. 首个真实 Skill 开发时，必须按本规范建立目录、SKILL.md、manifest.yaml、CHANGELOG.md 和验证记录。
4. 在没有实际验证之前，所有候选能力只能标记为 Draft。
5. 不因《穿越》项目中已有某种方法，就直接宣称该方法已跨项目验证。
6. 《穿越》的项目级 Skill 清单只登记实际采用并锁定的能力，不预先列入全部候选模块。
7. ChatGPT Web 版如何读取、确认和调用 GitHub 中的 Skill，由第三个交付物《ChatGPT Project—GitHub Skill 调用规范》规定；本规范不假设自动同步或自动加载。

## 14. 本规范的修订

本规范自身采用独立版本号。

- PATCH：不改变治理要求的文字澄清、错漏修正。
- MINOR：增加不破坏现有规则的新流程、字段或治理机制。
- MAJOR：改变核心目录契约、版本策略、成熟度门槛、项目锁定或发布治理方式。

每次修订必须记录变更原因、影响范围、兼容性和迁移要求。

## 规范总结

本规范确立以下长期规则：

1. 每项 Skill 都有稳定 ID、独立目录、主说明、结构化元数据、变更记录和验证证据。
2. 成熟度与生命周期分开管理；成熟度必须由实际项目和评测证据支持。
3. 每项 Skill 独立采用语义化版本；正式发布版本绑定不可歧义的 Git commit 和 tag。
4. 小说项目通过 PROJECT_SKILLS.md 锁定精确版本，不隐式跟随 main 或 latest。
5. 任何升级都必须评估兼容性、回归验证并经项目负责人确认。
6. 弃用、归档和回滚保留历史，不删除或改写已发布版本。
7. 通用方法、类型扩展和单部小说项目资料保持分离。

这套治理机制的目标，是让创作能力能够被重复使用、可靠组合、持续验证和安全升级，而不是让小说项目被不断变化的工具版本牵着走。
