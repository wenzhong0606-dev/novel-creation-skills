# 通用小说创作 Skill 体系架构 V0.1

- **文档编号：** NCS-ARCH-001
- **版本：** 0.1.1
- **状态：** 初始架构基线
- **适用范围：** 长期面向可复用创作方法、工作流与Skill；当前唯一实战验证项目为《穿越》
- **权威仓库：** https://github.com/wenzhong0606-dev/novel-creation-skills
- **本版定位：** 确定能力架构、边界和演进原则；不代表全部 Skill 已经实现或验证

---

## 1. 建设目标

建立一套能够跨聊天复用、并在具备真实需求时支持跨项目和跨类型复用的创作能力体系，使项目能够按需调用成熟方法，而不必从头重复研究。当前实施和验证以《穿越》为唯一实际项目；可复用架构是长期设计方向，不代表当前必须建设第二个小说项目。

体系需要具备以下能力：

1. 将复杂创作任务拆解为职责清晰的能力模块。
2. 按小说项目所处状态和当前任务，选择适当的工作流与专项能力。
3. 支持多个 Skill 协同、迭代和质量检查。
4. 区分通用方法、小说类型方法和单部小说的项目专属资料。
5. 通过版本锁定，使不同小说项目能够稳定使用指定版本的能力。
6. 以真实创作结果持续验证和改进方法。
7. 保留方法的来源、适用范围、验证证据和演进历史。

本体系不是提示词的简单集合，而是由方法规范、执行流程、输入输出契约、质量标准、评测案例和版本治理共同构成的创作基础设施。

## 2. 架构决策摘要

本版确定以下架构决策：

| 决策项 | 结论 | 理由 |
|---|---|---|
| 功能架构 | 保留三层 | 总控、工作流、专项能力的职责边界清楚 |
| 小说类型 | 横向扩展包，不设第四层 | 类型约束会横跨多个工作流，不是单一上下级层次 |
| 人物体系设计 | 独立工作流 Skill | 研究对象、产出和质量标准独立 |
| 情绪架构设计 | 独立工作流 Skill | 研究对象、产出和质量标准独立 |
| 人物与情绪关系 | 双向协同、允许迭代 | 人物变化产生情绪，情绪目标也影响人物与事件设计 |
| 项目资料 | 各小说项目独立维护 | 防止项目设定污染通用方法 |
| 首个验证项目 | 《穿越》 | 作为实战验证项目，但不等同于通用体系本身 |

## 3. 三层功能架构

### 3.1 第一层：总控层（Orchestration）

核心模块：**Novel Project Orchestrator**。

职责：

- 识别当前项目、项目状态和用户当前任务。
- 读取项目级约束、决策记录和进度。
- 判断任务属于哪类创作工作。
- 检查必要输入和前置条件是否齐备。
- 选择并调用适当的创作工作流 Skill。
- 根据工作流需要调用专项能力 Skill。
- 协调多个 Skill 的依赖、顺序和结果冲突。
- 检查产出是否符合项目约束和质量要求。
- 将完成情况转化为项目状态更新和下一步任务建议。
- 在跨聊天继续工作时，优先恢复已确认的项目状态和决策。

总控层负责工作组织和调度，不取代各专业 Skill 的实质判断，也不应把所有专业方法重复写进总控 Skill。

### 3.2 第二层：创作工作流层（Creative Workflows）

本层承担具有相对完整目标、输入、过程和交付物的创作工作。

这里使用“工作流层”而非“阶段层”，因为有些创作工作并非只在一个时间点执行一次。例如人物设计和情绪架构会贯穿全书规划、故事单元设计、章节设计和修订过程。

候选工作流模块如下：

| 编号 | 模块 | 主要职责 |
|---|---|---|
| W01 | 创意开发与小说立项 | 核心创意、类型定位、读者承诺、创作边界 |
| W02 | 故事总体架构 | 主题、核心冲突、故事引擎、主线与整体结构 |
| W03 | 全书路线与阶段规划 | 卷、部、阶段划分及其递进关系 |
| W04 | 故事单元规划 | 单元目标、冲突、因果、过程和结局 |
| W05 | 人物体系设计 | 人物功能、动机、关系、人物弧光与行为逻辑 |
| W06 | 情绪架构设计 | 情绪承诺、情绪曲线、张弛、转折与情绪回报 |
| W07 | 章节与场景设计 | 章节目标、场景组织、节奏、悬念和转折 |
| W08 | 正文创作 | 根据已确认的设计和项目约束完成文本 |
| W09 | 修订与结构重构 | 诊断问题、制定修改方案、执行局部或整体重构 |
| W10 | 质量评审与阶段验收 | 独立评审、证据核对、质量校准和验收判断 |

该清单是能力规划，不意味着所有模块现在已经存在，也不要求每部小说都按固定顺序调用全部模块。

#### 3.2.1 人物体系设计与情绪架构设计：独立模块

**W05 人物体系设计**主要回答：

- 人物是谁，在故事中承担什么功能？
- 人物的欲望、需求、目标、恐惧和矛盾是什么？
- 人物为什么采取某种行动？
- 人物之间如何形成关系、利益和冲突？
- 人物在故事中如何变化，变化由什么事件和选择推动？
- 人物掌握什么信息，何时获得或失去信息？

典型交付物包括人物档案、人物关系网络、人物动机与冲突表、人物弧光、关键选择和行为约束。

**W06 情绪架构设计**主要回答：

- 小说向读者承诺怎样的核心情绪体验？
- 不同阶段希望读者产生、维持或转换哪些情绪？
- 情绪如何积累、强化、延宕、释放和回收？
- 哪些事件构成情绪转折和情绪回报？
- 全书、阶段、故事单元和章节之间如何形成情绪层次？
- 情绪效果是否由人物、事件和文本自然产生，而不是依靠说明强行告知？

典型交付物包括核心情绪承诺、全书及阶段情绪曲线、情绪节点、张弛安排、情绪回报设计和局部情绪检查标准。

两者必须独立维护各自的目标、输入、产出和质量标准，但通过协同接口共同工作：

1. 人物的选择、关系变化和命运转折，应当能够解释其预期情绪影响。
2. 情绪目标可以反向提出人物关系、人物选择或事件设计需求。
3. 当人物逻辑与情绪目标冲突时，不能以牺牲人物可信度为代价强行制造情绪。
4. 两个模块允许多轮往返修订，不设置僵硬的单向先后关系。
5. 总控层负责识别冲突并组织协调；两个模块分别对本领域的设计质量负责。

### 3.3 第三层：专项能力层（Specialized Capabilities）

本层由边界清楚、可以被多个工作流重复调用的专项能力组成。

初步候选包括：

| 编号 | 专项能力 | 核心检查或任务 |
|---|---|---|
| S01 | 因果链审查 | 事件动因、条件、结果及因果闭合 |
| S02 | 伏笔与回收审查 | 线索铺设、可识别性、公平性与兑现 |
| S03 | 人物行为一致性 | 行为是否符合动机、认知、能力和既有经历 |
| S04 | 时空连续性审查 | 时间、空间、行动路径和场景衔接 |
| S05 | 设定与资源约束核对 | 规则、物品、数字、资源及其使用限制 |
| S06 | 盲审材料制作 | 去除不必要提示，形成独立阅读材料 |
| S07 | 多轮评审差异分析 | 识别评审结论、证据和分歧 |
| S08 | 质量标准与评分校准 | 统一评价维度、等级和判定尺度 |
| S09 | 评审问题转化 | 将问题转化为可执行、可验收的修改任务 |
| S10 | 项目状态恢复与交接 | 形成跨聊天可恢复的状态、决策和待办信息 |

专项能力可以被多个工作流调用；专项能力本身不负责统筹整部小说，也不应越权修改项目的已确认设定和决策。

## 4. 横向扩展机制：小说类型扩展包

小说类型不是第四个功能层，而是横跨三层的专业约束与方法扩展。

类型扩展包可以包含：

- 类型读者承诺与类型惯例。
- 类型特有的故事结构方法。
- 类型特有的人物关系与情绪机制。
- 类型特有的专项审查规则。
- 类型专属质量评审维度。
- 类型术语、参考资料和测试案例。

例如：

| 类型扩展包 | 可能覆盖的专业问题 |
|---|---|
| 悬疑 | 谜题结构、线索公平性、信息控制、真相揭示 |
| 科幻 | 技术规则、科学约束、设定一致性、推演边界 |
| 历史 | 时代背景、制度环境、历史事实与虚构边界 |
| 冒险 | 探索、风险递进、空间行动、资源消耗 |
| 爱情 | 关系推进、情感阻力、关系转折与情绪兑现 |

类型扩展包可以被总控层识别并配置给相关工作流，也可以为专项能力提供类型化检查规则。

类型扩展包不得未经声明就覆盖通用方法或项目已经确认的约束。若某种类型惯例与具体项目的创作意图冲突，应由项目决策明确取舍。

## 5. 三类知识资产的边界

必须严格区分：

### 5.1 通用创作能力

适用于多个项目的创作方法，例如因果设计、人物动机分析、情绪架构、伏笔管理、章节节奏和质量评审。

存放于本仓库。

### 5.2 小说类型专属能力

适用于某一类小说的专业方法和约束，例如悬疑线索公平性、科幻技术规则。

存放于本仓库的类型扩展目录。

### 5.3 单部小说项目资产

只对某一部小说成立的内容，例如：

- 世界观、背景设定和规则。
- 人物档案及关系。
- 故事总纲和阶段路线。
- 情绪规划和故事单元规划。
- 正文、修订稿和历史版本。
- 已确认的创作决策。
- 项目状态、评审记录和待办任务。

存放于对应小说的独立项目仓库，不复制到通用 Skill 仓库作为通用事实。

## 6. Skill 的基本契约

每个正式 Skill 不应只是一个名称或一段指令。至少应明确：

1. **身份与职责：** Skill 负责什么，不负责什么。
2. **触发条件：** 什么任务或情境下应当调用。
3. **输入要求：** 必须读取哪些材料，缺少什么时如何处理。
4. **前置条件：** 开始执行前必须满足什么。
5. **执行方法：** 具体步骤、判断规则和必要分支。
6. **输出契约：** 应交付什么，采用什么结构。
7. **质量标准：** 如何判断完成质量。
8. **边界与冲突处理：** 哪些决定不能擅自做，冲突交给谁处理。
9. **依赖关系：** 可能调用哪些其他 Skill，接受哪些上游产出。
10. **验证案例：** 用什么实际任务或测试案例验证能力。
11. **版本与成熟度：** 当前版本、适用范围和验证状态。

Skill 的拆分以职责独立、输入输出清楚、可重复调用和可独立验证为依据，不以追求模块数量为目的。

## 7. 调用与协同关系

基本调用链：

1. 总控层读取项目状态和当前任务。
2. 总控层选择一个或多个创作工作流。
3. 工作流检查输入和前置条件。
4. 工作流按需调用专项能力。
5. 工作流整合专项能力的结果，形成专业交付物。
6. 总控层检查交付物是否符合项目约束、任务目标和验收标准。
7. 完成后更新项目状态，并明确下一步工作。

调用原则：

- 总控层负责调度，不包办专业判断。
- 工作流负责完整任务，不重复实现所有专项检查。
- 专项能力负责清晰边界内的具体工作，不擅自改变整体规划。
- 多个 Skill 的结论冲突时，必须显式列出冲突、依据和影响，不得静默合并。
- 项目已经确认的决策优先于未经批准的通用建议；如发现重大问题，应提出变更建议并等待决策。
- 不要求所有工作都机械经过全部层级；根据任务复杂度调用必要能力。

## 8. GitHub 仓库与小说项目的关系

### 8.1 权威来源

本仓库是通用创作方法、Skill、类型扩展、模板、评测和治理规范的权威来源。

每部小说的项目仓库是该小说正文、设定、决策、状态和历史记录的权威来源。

二者分离，避免通用方法被项目资料污染，也避免不同小说之间相互覆盖。

### 8.2 项目级 Skill 清单

每部小说项目应维护 `PROJECT_SKILLS.md`，至少记录：

- Skill 标识与名称。
- 来源仓库和文件路径。
- 使用版本或 Git 标签。
- 必要时记录精确 commit SHA。
- 本项目启用、禁用或覆盖的配置。
- 项目专属的适配说明。

项目可以只引用实际需要的 Skill，不要求每个项目安装全部能力。

### 8.3 执行环境边界

ChatGPT 是主要的交互与执行环境；GitHub 是通用 Skill 的权威存储和版本管理环境。

必须区分“仓库中存在 Skill”与“当前 ChatGPT 会话已经读取并使用 Skill”。不能假设 ChatGPT Web 版会因为项目中写有 GitHub 地址，就自动读取仓库全部内容或自动加载 Skill。

具体读取、引用、版本锁定和执行方式由独立的《ChatGPT Project—GitHub Skill 调用规范》确定。

## 9. 建议仓库结构

本版建议采用以下结构，后续根据真实 Skill 的数量和依赖关系调整：

```text
novel-creation-skills/
├── README.md
├── VERSION
├── CHANGELOG.md
├── SKILL_INDEX.md
├── docs/
│   ├── architecture/
│   │   └── novel-creation-skill-architecture-v0.1.md
│   ├── governance/
│   └── integration/
├── skills/
│   ├── orchestrator/
│   ├── workflows/
│   └── specialized/
├── extensions/
│   └── genres/
├── templates/
└── evaluations/
```

说明：

- `skills/orchestrator/`：总控 Skill。
- `skills/workflows/`：创作工作流 Skill。
- `skills/specialized/`：专项能力 Skill。
- `extensions/genres/`：小说类型扩展包。
- `templates/`：可复用工作模板。
- `evaluations/`：测试案例、评测标准和验证记录。
- `docs/governance/`：版本、成熟度和变更治理规范。
- `docs/integration/`：ChatGPT Project 与 GitHub 的调用规范。

当前不提前创建全部空模块；只有在具体能力开始开发时才建立相应目录和文件。

## 10. 版本与成熟度治理

### 10.1 Skill 成熟度

| 状态 | 定义 |
|---|---|
| Draft | 已形成设计，尚未进入真实任务验证 |
| Experimental | 已在真实任务中试用，方法仍可能明显变化 |
| Project-validated | 已在至少一个明确项目中完成实际验证 |
| Cross-project-validated | 已在不同小说项目中验证，且验证结果支持复用 |
| Stable | 适用范围、输入输出、质量标准和失败边界均较清楚，具备可重复使用的证据 |

成熟度必须由验证证据支持，不能仅凭主观评价升级。

### 10.2 变更记录

重要变更至少记录：

- 问题及其出现背景。
- 原方法和具体不足。
- 支持判断的文本、评审或执行证据。
- 修改内容及预期改善。
- 实际验证结果。
- 对兼容性、调用方式和项目配置的影响。

### 10.3 版本原则

- 小范围兼容性改进采用小版本迭代。
- 输入输出、调用方式或能力边界发生不兼容变化时，应明确记录重大版本变化。
- 项目应锁定已采用的版本，不因通用仓库更新而默认改变正在执行的项目方法。
- 已发布版本应保留历史记录，不能用新版本静默覆盖旧版本的含义。

具体版本编号、发布流程和升级审批方式在独立治理规范中进一步确定。

## 11. 《穿越》的验证定位

《穿越》是本体系当前且唯一的实战验证项目。

当前已批准的《穿越》创作方法 V1.0 是该项目的正式执行基线。它可以作为提取候选能力的重要来源，但不能直接等同于本体系的通用 Skill 版本。

提取和验证时应遵守：

1. 先识别方法解决的问题和适用条件。
2. 区分通用原则、项目特定规则和类型特定规则。
3. 将候选方法封装为有明确输入输出的 Skill。
4. 在《穿越》的真实任务中验证可执行性、交付质量和失败边界。
5. 记录例外条件、失败情况及需要人工判断的边界。

当前不建设第二部小说，不安排跨项目验证。若未来确实出现其他小说项目及复用需求，再将跨项目验证作为独立、可选的后续工作；不得把它设为《穿越》项目内使用或验收Skill的前置条件。

《穿越》中的一次成功不能单独证明跨类型通用性；同样，缺少第二个项目也不妨碍在明确的《穿越》适用范围内验证和维护Skill。

## 12. 体系建设路线

### 第一阶段：架构与治理基础

**状态：已完成基础交付与一致性收尾。**

已建立三项基础交付物：

### 第三阶段：《穿越》实战验证

在《穿越》的真实创作任务中反复验证Skill的输入要求、执行稳定性、交付质量、失败处理和协同效果。达到相应证据门槛后，可在明确的项目适用范围内升级成熟度。

### 第四阶段：跨项目验证（可选）

只有未来出现第二个真实小说项目，并且存在明确的复用需求时，才考虑在不同项目中检验方法通用性。此阶段不是当前计划，不是《穿越》项目内正式使用Skill的前置条件；若长期没有第二个项目需求，可以不启动。

### 第五阶段：通用体系定型（按实际需求决定）

当确实需要向多个项目提供统一能力时，再依据跨项目证据、调用规范和版本治理情况评估是否发布通用体系V1.0。若当前只有《穿越》一个项目，则以项目内已验证、范围明确的Skill为交付目标，不必等待整套通用体系定型。

## 13. 本阶段明确不做的事情

- 不一次性开发全部候选 Skill。
- 不为追求层级数量增加没有必要的架构层。
- 不将人物体系与情绪架构合并为一个职责过宽的模块。
- 不把单部小说的设定和特殊规则写入通用方法。
- 不将《穿越》创作方法 V1.0 直接改名为通用 Skill V1.0。
- 不假设 ChatGPT Web 版自动同步或自动加载 GitHub 仓库内容。
- 不以 Skill 数量、文档数量或提示词长度衡量成熟度。
- 不为建设通用体系而擅自改变《穿越》已经批准的创作基线。

## 架构基线总结

本体系采用**三层功能架构 + 横向小说类型扩展包**。

总控层负责组织和调度；创作工作流层承担完整创作任务；专项能力层提供可重复调用的专业能力。人物体系设计和情绪架构设计作为两个独立工作流模块协同迭代。

通用能力、类型扩展和单部小说项目资料分别管理。GitHub 保存通用能力的权威版本，各小说项目独立维护自身资料并锁定所引用的 Skill 版本。

以《穿越》作为当前唯一实战验证项目，形成可维护、可扩展、可持续改进的创作Skill资产；只有未来出现真实的其他项目需求时，才启动跨项目验证与扩展。
