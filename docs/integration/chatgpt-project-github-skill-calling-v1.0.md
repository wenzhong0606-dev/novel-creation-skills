## 1. 目的与核心原则

本规范定义 ChatGPT Project、小说项目 GitHub 仓库和通用 Skill GitHub 仓库之间的协作方式，确保创作任务可以跨聊天恢复、按需调用 Skill、核验实际版本并保留可追溯记录。

本规范不把 GitHub 仓库链接等同于 Skill 已加载，也不把 ChatGPT 的聊天记忆等同于项目正式状态。

### 1.1 三个环境的职责

| 环境 | 权威职责 | 不承担的职责 |
|---|---|---|
| 通用 Skill GitHub 仓库 | 保存通用方法、Skill、类型扩展、模板、评测和治理规范的权威版本 | 不保存某部小说的专属世界观、人物事实、正文和项目决策 |
| 单部小说 GitHub 项目仓库 | 保存该小说的正文、设定、路线规划、人物关系、情绪规划、决策、进度和项目级 Skill 锁定 | 不取代通用 Skill 仓库，不把项目专属事实上升为通用方法 |
| ChatGPT Project | 提供项目指令、相关聊天、参考文件和工具调用环境，承载分析、规划、创作、评审和交接 | 不作为 GitHub 内容的自动镜像，不取代两个 GitHub 仓库的权威存储 |

### 1.2 必须遵守的原则

1. **双仓库分离**：通用 Skill 与单部小说项目资料分别保存在各自仓库。
2. **Project 是工作环境，不是唯一事实库**：重要项目状态、决策和版本锁定必须写回小说项目仓库。
3. **按需加载**：只读取当前任务需要的 Skill 及其依赖，不要求每次载入整个 Skill 仓库。
4. **先锁版本，再执行**：先读取项目的 PROJECT_SKILLS.md，再按精确 commit SHA 获取 Skill 文件。
5. **读取必须可核验**：不能只凭仓库地址、文件名、旧聊天摘要或模型记忆声称已加载 Skill。
6. **禁止静默升级**：不得把 main、latest 或当前默认分支自动当作项目锁定版本。
7. **项目决策优先**：通用 Skill 与小说项目已批准的决策冲突时，必须报告冲突，不得擅自覆盖项目基线。
8. **跨聊天以状态文件为准**：新聊天必须重新确认项目状态、当前任务和 Skill 版本，不得假设旧聊天内容完整可见。

## 2. ChatGPT Web 版的实际能力边界

本节用于防止把产品能力假设成自动化机制。产品界面、连接器名称、套餐可用性和工作区策略可能变化；执行时应以当时实际可用的功能及 OpenAI 官方说明为准。

### 2.1 ChatGPT Project 能做什么

Project 可以集中保存相关聊天、项目指令和上传的参考文件；项目聊天可以利用这些上下文继续工作。Project 指令只在对应项目内生效。Project 中也可以使用当前账户和工作区允许的连接应用。

因此，Project 适合保存：

- 稳定的项目协作指令。
- 项目启动说明和当前状态快照。
- 项目级 Skill 锁定清单的工作副本。
- 当前阶段正在使用的关键参考文件。
- 重要决策摘要和跨聊天交接材料。

Project 文件是工作副本，不自动成为 GitHub 仓库的最新版本。若 GitHub 文件更新，必须重新读取或替换 Project 中的旧副本，并核对 commit SHA。

### 2.2 GitHub 连接器能做什么

在支持且已授权的 ChatGPT 使用环境中，GitHub 连接器可以按需检索获准仓库的内容，包括 README、代码和文档。

必须理解以下边界：

- GitHub 连接属于按需读取，不等于把仓库持续同步到 ChatGPT。
- 官方 GitHub 连接器不会因此创建一个可假定始终最新的仓库索引。
- 可用性会因套餐、工作区和产品界面而不同；某个环境能在深度研究或 Work 中访问，不代表标准聊天中一定可用。
- 仓库必须已经授权给连接的 GitHub 应用；私有仓库还要检查安装账户、仓库选择和组织审批。
- 官方 ChatGPT GitHub 应用的标准能力是只读检索。不能假设它可以直接创建文件、提交修改或推送 PR。

### 2.3 Project 来源与 GitHub 链接的区别

不能把 GitHub 仓库 URL 直接粘贴到 Project 来源区域，就假设仓库已被同步或 Skill 已加载。

Project 来源中支持的应用链接类型以当前产品界面为准。即使 Project 可以调用已连接应用，GitHub 内容仍应按需读取并核验版本；不能把普通链接当成持续同步的 Skill 安装。

### 2.4 写入 GitHub 的能力边界

写入方式取决于当前环境：

1. 若当前 ChatGPT 环境提供有明确授权的 GitHub 写入操作，可以在权限允许范围内创建或更新文件；提交后必须重新读取验证。
2. 若只有官方 GitHub 只读连接器，应使用支持写入的 Codex 工作流、Git 客户端或 GitHub 网页操作完成提交。
3. 若当前环境无法写入，应提供完整修改内容或补丁，由用户确认和提交。
4. 无论采用哪种方式，都不得在提交成功前声称文件已更新；不得在未重新读取的情况下声称已验证。

### 2.5 产品能力依据

本规范的产品边界依据以下 OpenAI 官方说明，并应在产品能力发生变化时复核：

- Projects in ChatGPT： https://help.openai.com/en/articles/10169521-projects-in-chatgpt
- Connecting GitHub to ChatGPT： https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt

## 3. 每部小说的 ChatGPT Project 配置

### 3.1 一个小说项目对应一个 ChatGPT Project

原则上，每部小说建立独立 ChatGPT Project，避免不同小说的设定、人物事实、项目决策和创作任务互相污染。

例如：

- ChatGPT Project：穿越
- 小说项目仓库：该小说自己的 GitHub 仓库
- 通用 Skill 仓库：novel-creation-skills

若未来需要对同一小说进行明确隔离的研究或实验，可以建立子 Project，但必须说明其与主项目的关系和资料来源。

### 3.2 Project Instructions 应放什么

Project Instructions 只放长期稳定、跨聊天都需要遵守的规则，不放频繁变化的章节进度、临时任务和长篇项目资料。

建议采用以下模板，替换尖括号中的占位内容后放入对应 Project 的项目指令：

~~~text
你正在协助创作小说《<小说名>》。

一、权威资料来源
1. 本小说 GitHub 仓库：<小说项目仓库 URL>
2. 通用 Skill 仓库：https://github.com/wenzhong0606-dev/novel-creation-skills
3. 小说项目仓库是本小说正文、设定、决策、状态和进度的权威来源。
4. 通用 Skill 仓库是通用创作方法、Skill、类型扩展和治理规范的权威来源。
5. ChatGPT Project 中的上传文件和聊天内容是工作上下文或快照；若与 GitHub 已确认版本冲突，必须指出冲突并核验，不得静默选择。

二、每次新任务的启动要求
1. 先恢复本小说当前状态，读取PROJECT_BOOTSTRAP.md、项目状态文件（PROJECT_STATE.md或等效文件，如CURRENT.md）、PROJECT_SKILLS.md和相关决策／ADR记录。
2. 明确当前任务、已批准基线、未完成事项和禁止擅自变更的内容。
3. 根据 PROJECT_SKILLS.md 选择本任务需要的 Skill。
4. 按锁定的 commit SHA 读取对应 manifest.yaml、SKILL.md 及必要依赖。
5. 核对读取到的版本、成熟度、生命周期和依赖；无法核验时不得声称已加载。
6. 在开始实质工作前，简要报告本次读取的项目状态版本和 Skill 版本。

三、创作与评审原则
1. 以项目已批准的设定、决策和创作基线为准。
2. 区分正文事实、人物猜想、转述、计划、承诺和实际结果。
3. 不以模型记忆或旧聊天摘要替代原始正文和权威项目资料。
4. 发现问题时区分确定硬伤、轻微问题和主观读感。
5. 不擅自改写正文、设定或已批准决策；先报告问题和修改建议，按用户授权执行。
6. 不把单一项目经验未经验证直接升级为通用 Skill。

四、跨聊天延续
1. 重要决策、状态、任务进度和交接信息必须形成项目记录。
2. 每轮工作结束时，说明完成项、未完成项、决策变化、文件变化和下一步任务。
3. 项目状态文件未更新时，不得把聊天中的临时结论当作已归档的正式状态。

五、版本与权限
1. 正式任务不得隐式使用 main、latest 或未锁定版本。
2. 不得擅自升级 PROJECT_SKILLS.md 中已锁定的 Skill。
3. GitHub 写入必须以当前可用权限为准；提交后重新读取验证。
4. 遇到资料缺失、版本冲突或权限不足时，明确停止点和所需补充，不得猜测补齐。
~~~

### 3.3 Project 中建议保留的文件

Project Sources 中只保留少量稳定、常用的文件：

| 文件 | 用途 | 是否建议常驻 |
|---|---|---|
| PROJECT_BOOTSTRAP.md | 项目入口、仓库地址、资料地图和启动顺序 | 是 |
| PROJECT_STATE.md或等效状态文件（如CURRENT.md） | 当前阶段、已完成工作、当前任务和待办 | 是 |
| PROJECT_SKILLS.md | 本项目采用的 Skill 及版本锁定 | 是 |
| DECISIONS.md或等效ADR记录目录／索引 | 已批准的关键决策及其状态 | 是 |
| 当前阶段核心规划 | 当前任务确实需要的规划基线 | 按阶段 |
| 全部 Skill 仓库文件 | 通用能力全集 | 否 |
| 全部小说正文与历史稿 | 全量历史资料 | 不建议全部常驻；按任务读取 |

如果 Project 中保存的是 GitHub 文件的手动上传副本，必须在文件说明中记录其来源路径、commit SHA 和读取日期。仓库更新后，旧副本必须标记为过期或替换，不能与新版本混用。

## 4. 小说项目仓库的最小入口约定

为使新聊天能够可靠恢复项目，小说项目仓库应提供以下入口文件。实际路径可以按项目现有结构调整，但必须在 PROJECT_BOOTSTRAP.md 中明确。

| 文件 | 核心内容 |
|---|---|
| PROJECT_BOOTSTRAP.md | 项目身份、仓库位置、权威文件地图、启动步骤、协作约束 |
| PROJECT_STATE.md或等效状态文件（如CURRENT.md） | 当前阶段、已完成工作、正在进行的任务、阻塞项和下一步 |
| PROJECT_SKILLS.md | 本项目启用的 Skill、版本、commit SHA、成熟度和适配配置 |
| DECISIONS.md或等效ADR记录目录／索引 | 已批准决策、撤回决策、待批准事项及证据来源 |

这些文件应短而可导航，不复制整部小说或全部历史聊天。

如果项目已经有等效的状态、决策或索引文件，不要求重复创建；只需在 PROJECT_BOOTSTRAP.md 中说明对应关系。例如，《穿越》以CURRENT.md作为PROJECT_STATE.md的等效状态入口，以decisions/ADR-*.md作为DECISIONS.md的等效决策记录；不得另建重复文件。

### 4.1 项目状态记录最低字段

项目状态文件（PROJECT_STATE.md或等效文件，如CURRENT.md）至少说明：

- 项目名称和当前项目基线版本。
- 当前所处创作阶段。
- 已完成的阶段和交付物。
- 当前任务及其验收标准。
- 尚未完成的任务和依赖。
- 当前阻塞问题。
- 最近一次状态更新时间。
- 关联的决策记录和正文/规划文件路径。

### 4.2 决策记录最低字段

每项关键决策至少包含：

- 决策 ID。
- 决策内容。
- 状态：Proposed、Approved、Rejected、Superseded 或 Withdrawn。
- 决策日期。
- 决策依据和影响范围。
- 关联文件或评审证据。
- 若被替代，指向替代决策。

聊天中出现“可以考虑”“我倾向于”“先试试”等表达，不自动视为 Approved。

## 5. PROJECT_SKILLS.md 的锁定格式

每部小说项目使用 PROJECT_SKILLS.md 记录实际采用的 Skill。推荐结构如下：

~~~markdown
# PROJECT_SKILLS.md

- 项目：<小说名>
- 项目仓库：<项目仓库 URL>
- 通用 Skill 仓库：https://github.com/wenzhong0606-dev/novel-creation-skills
- 最近复核：<YYYY-MM-DD>

## 已启用 Skill

| ID | 名称 | 版本 | 成熟度 | 状态 | 路径 | Git Tag | Commit SHA |
|---|---|---|---|---|---|---|---|
| workflow-example | 示例工作流 | 0.1.0 | Experimental | Trial | skills/workflows/workflow-example/ | 无 | <完整 SHA> |

## 依赖锁定

| 被调用 Skill | 依赖 Skill | 依赖版本 | Commit SHA |
|---|---|---|---|
| <Skill ID> | <Dependency ID> | <版本> | <完整 SHA> |

## 项目适配

- 适配项：
- 适配原因：
- 影响的默认规则：
- 是否改变 Skill 原有行为：
- 批准记录：

## 禁用或暂不采用

| ID | 原因 | 复核条件 |
|---|---|---|
~~~

规则：

1. 只登记真实采用的 Skill，不把架构规划中的候选模块当作已存在的 Skill。
2. 正式使用必须记录完整 commit SHA；不能只写 main 或 latest。
3. 若 Skill 尚无正式 tag，可以锁定明确 commit，但必须标记 Trial，并遵守治理规范的实验使用门槛。
4. manifest.yaml 与 SKILL.md 必须来自同一锁定 commit。
5. 所有关键依赖都要锁定；不能让依赖版本漂移。
6. 成熟度和生命周期以锁定版本中的 manifest.yaml 为准。
7. 项目升级后更新此文件，并保留升级前后的版本记录。

## 6. 每次新聊天的标准启动流程

新聊天不应直接进入正文创作或复杂分析。先完成项目恢复和 Skill 加载确认。

### 6.1 第一步：识别项目

确认当前 ChatGPT Project、小说项目仓库和用户当前任务。若项目身份不清楚，先询问一个必要问题，不得自行猜测。

### 6.2 第二步：恢复项目状态

从小说项目仓库读取：

1. PROJECT_BOOTSTRAP.md。
2. 项目状态文件（PROJECT_STATE.md或等效文件，如CURRENT.md）。
3. PROJECT_SKILLS.md。
4. 与当前任务有关的DECISIONS.md条目或ADR记录。
5. 当前任务涉及的规划、正文或评审材料。

读取时优先使用明确文件路径和项目仓库；不要只搜索项目名称后凭搜索摘要推断项目状态。

### 6.3 第三步：解析 Skill 清单

- 读取 PROJECT_SKILLS.md。
- 识别本次任务真正需要的工作流 Skill。
- 由总控层判断是否需要专项能力和类型扩展包。
- 读取各 Skill 的依赖声明。
- 只加载当前任务所需的模块。

不能因为某个 Skill 已在项目清单中启用，就认为每项任务都必须调用它。

### 6.4 第四步：按锁定版本读取 Skill

每个被调用的 Skill 至少读取：

- 对应 commit 下的 manifest.yaml。
- 同一 commit 下的 SKILL.md。
- 执行需要的 references、templates 和依赖文件。

必须核对：

- 文件路径与 ID 一致。
- manifest 中的版本与 PROJECT_SKILLS.md 一致。
- 成熟度与生命周期符合使用条件。
- 文件确实来自锁定 commit。
- 依赖版本和 SHA 已确认。

如果连接器不能按指定 commit 读取，必须改用手动提供该 commit 的文件快照，或者暂停执行。不得悄悄退回 main。

### 6.5 第五步：给出加载收据

在实质工作前，用简短清单报告：

~~~text
项目恢复与 Skill 加载确认

小说项目：
项目仓库：
项目状态来源：
项目状态对应 commit：
当前阶段：
当前任务：

本次加载的 Skill：
- ID / 名称：
- 版本：
- 成熟度：
- Git Tag：
- Commit SHA：
- 依赖是否核验：

资料完整性：
- 已读取：
- 缺失：
- 冲突：
- 是否允许开始执行：
~~~

若没有加载任何 Skill，应明确说明“本次未加载专用 Skill，以下使用一般模型能力完成”，不得虚构 Skill 调用记录。

### 6.6 第六步：确认后开始工作

当项目状态、关键约束和 Skill 版本可核验时，开始执行任务。若有影响结论的资料缺失或版本冲突，应先报告并解决。

## 7. 任务执行与多 Skill 协作

### 7.1 调用顺序

遵循架构文件规定的基本关系：

1. 总控层识别任务、项目状态和约束。
2. 选择必要的创作工作流。
3. 工作流检查输入和前置条件。
4. 按需调用专项能力。
5. 工作流整合专业结果。
6. 总控层检查产出是否符合任务和项目约束。
7. 记录状态、决策和后续任务。

### 7.2 不同任务的调用策略

| 任务类型 | 主要工作流 | 可选专项能力 |
|---|---|---|
| 新小说立项 | 创意开发与小说立项 | 类型扩展、质量标准校准 |
| 全书规划 | 故事总体架构、全书路线与阶段规划 | 因果链、人物一致性、情绪检查 |
| 人物设计 | 人物体系设计 | 人物行为一致性、关系冲突检查 |
| 情绪规划 | 情绪架构设计 | 情绪曲线与回报检查 |
| 故事单元规划 | 故事单元规划 | 因果链、伏笔、人物行为、时空连续性 |
| 章节设计 | 章节与场景设计 | 因果链、悬念、节奏和连续性 |
| 正文创作 | 正文创作 | 相关设定、人物一致性和连续性检查 |
| 修订 | 修订与结构重构 | 问题分类、因果、伏笔、连续性和质量评审 |
| 独立评审 | 质量评审与阶段验收 | 盲审材料、多轮差异分析、评分校准 |

该表是调用参考，不是固定的强制流水线。总控层应根据任务目标和风险选择最小充分组合。

### 7.3 多 Skill 结论冲突

发生冲突时必须：

1. 列出各 Skill 的结论和证据。
2. 说明冲突来自适用范围、输入差异、规则矛盾还是判断分歧。
3. 检查项目已批准的决策。
4. 判断是否需要补充资料或重新执行某项检查。
5. 将未解决冲突交给项目负责人决策。

不得把冲突结果简单平均，也不得静默选择更符合模型直觉的一方。

## 8. 无法连接 GitHub 时的降级方案

当 GitHub 连接器不可用、仓库未授权、文件无法读取或当前产品界面不支持相关能力时，按以下顺序处理。

### 8.1 首选：授权的 GitHub 连接器

- 确认连接的 GitHub 账户。
- 确认目标仓库已授权。
- 使用仓库全名和准确文件路径读取。
- 读取时指定项目锁定的 tag 或 commit SHA。
- 记录读取结果和版本。

### 8.2 备选：手动提供精确版本文件

由用户从 GitHub 的指定 commit 下载或复制本次所需文件，并上传到 ChatGPT Project 或当前聊天。

至少提供：

- manifest.yaml。
- SKILL.md。
- 被调用的依赖 Skill 文件。
- 必要的 references 或 templates。
- 文件来源 URL 和完整 commit SHA。

上传文件应在名称或说明中标明版本和 SHA，避免多个版本混淆。

### 8.3 禁止的降级行为

- 不得用旧聊天中的 Skill 摘要代替当前版本全文。
- 不得用 main 上的最新文件替代锁定版本。
- 不得将同一 Skill 不同 commit 的 manifest 和 SKILL.md 混用。
- 不得在未读取时声称“已加载”。
- 不得因为 GitHub 访问失败，就自动把项目清单中的 Skill 当作一般提示词执行。

若无法获得足够材料，暂停该 Skill 的正式调用，并说明需要用户提供什么。

## 10. Skill 升级与项目兼容

当通用 Skill 仓库发布新版本时：

1. 不自动升级小说项目。
2. 比较新旧版本的 CHANGELOG、manifest 和 SKILL.md。
3. 检查 MAJOR、MINOR、PATCH 变化及其兼容影响。
4. 选取当前小说项目中有代表性的旧任务进行回归验证。
5. 检查对已批准规划、正文、人物逻辑和质量标准的影响。
6. 形成升级建议，明确收益、风险和迁移成本。
7. 由项目负责人批准后更新 PROJECT_SKILLS.md。
8. 保留原版本锁定记录，以便回滚。

如果新版本修复了严重错误，应优先评估风险，但仍须明确记录项目是否升级及其依据。

<在这里写具体任务>

## 14. 当前体系的落地顺序

三项基础交付物完成后，建议按以下顺序应用：

1. 在当前《穿越》ChatGPT Project中维护稳定的Project Instructions。
2. 在《穿越》仓库中使用既有的PROJECT_BOOTSTRAP.md、CURRENT.md、PROJECT_SKILLS.md和decisions/ADR-*.md；等效文件已存在时不重复创建。
3. 从通用Skill仓库按需读取实际已开发、已锁定的Skill；尚未开发的能力不提前假装存在。
4. 先在《穿越》项目中验证跨聊天恢复、Skill加载收据、版本锁定和任务收尾流程，并根据真实任务改进。
5. 只有未来出现其他小说项目及明确复用需求时，才评估复制配置和跨项目验证；当前不创建第二个项目，也不把该步骤列为待办。

## 规范总结

本规范建立的工作机制是：

- **GitHub 通用 Skill 仓库**提供可复用能力的权威版本。
- **小说项目 GitHub 仓库**保存该小说的权威事实、决策、进度和 Skill 版本锁定。
- **ChatGPT Project**提供持续的工作上下文和执行环境。
- **每次新聊天**先恢复项目状态，再按锁定 SHA 读取必要 Skill，并输出加载收据。
- **每轮任务结束**将正式状态、决策和交接信息写回项目仓库。
- **版本升级**由项目负责人批准，不自动影响现有小说项目。

最终目标不是让 ChatGPT 依赖聊天记忆“记住一切”，而是让每次新聊天都能通过明确的项目入口、状态记录和 Skill 版本锁定，可靠恢复工作并继续推进。
